## When to Use
When refactoring the dual-write pattern across domain services in T1D Companion. The pattern: 16 domain services each duplicate "write domain table → write HealthMetric" logic.

## Procedure
## Procedure

1. **Discover pattern**: Use `improve-codebase-architecture` (or manual grep) to identify dual-write duplication:
   ```bash
   grep -rl "write_metric_if_present" app/*/service.py | sort
   ```
2. **Write TDD tests first (red phase)**: Create `tests/test_metric_registry.py`
   - `record_metric()`: single metric with validation (skip None/negative)
   - `record_metrics_batch()`: atomic batch for multi-metric entries
   - Edge cases: None values, negative values, metadata passthrough
3. **Implement MetricRegistry service**: `app/services/metric_registry.py`
   - Accept `AsyncSession` and optionally `user_id` in constructor
   - `record_metric()`: skips None/negative values, returns `HealthMetric | None`
   - `record_metrics_batch()`: atomic via `_record_metric` with `flush()`
4. **Run tests (green phase)** — verify 6/6 passing before refactoring services
5. **Bulk-refactor domain services** (14 services, iterative):
   - Change import: `from app.services.metric_writer import write_metric_if_present` → `from app.services.metric_registry import MetricRegistry`
   - Add `self._metric_registry = MetricRegistry(db)` in `__init__`
   - Replace `await write_metric_if_present(...)` calls with `await self._metric_registry.record_metric(...)`
   - **Pitfall**: After changing import, `write_metric_if_present` references in `create()` methods must use the new `self._metric_registry.record_metric()` pattern — do both edits in one pass or re-read the file
   - For services with complex multi-metric entries (food with 6 metrics): use `record_metrics_batch()`
6. **Verify no old imports remain**:
   ```bash
   grep -rn "metric_writer" app/*/service.py
   # Should return empty
   ```
7. **Deprecate old module**: Add `DeprecationWarning` to `app/services/metric_writer.py`
8. **Run full test suite** to catch regressions:
   ```bash
   pytest --tb=short -q  # Expect 324+ tests passing
   ```
9. **Document the architecture**:
   - Write ADR at `docs/adr/NNN-metric-name.md` with: Context, Decision (the MetricRegistry pattern), Consequences (pros/cons), and Migration notes (14 files changed)
   - Update `CONTEXT.md` domain glossary with new terms (e.g. "MetricRegistry", "batch recording")
## Pitfalls
## Pitfalls

- **Import + callsite in one pass**: When changing a service's import from `metric_writer` to `MetricRegistry`, the `write_metric_if_present(...)` calls must also change to `self._metric_registry.record_metric(...)`. If the import edit doesn't include the callsite edit, the build will fail. Do both edits per file or re-read the file after changing the import.
- **Duplicate edits on same file**: If a service has `write_metric_if_present` in both imports and callsites, each `edit()` call must target uniquely matching blocks — you cannot change the import and the callsite in overlapping edits. Make them as two separate, non-overlapping `edit` entries, or if they're far apart, use separate `edit()` calls.
- **Blood pressure already refactored**: Some services may already have been migrated mid-session — always re-read the file before editing rather than assuming the original pattern.
- **Measurements service trick**: After changing the import, the constructor didn't initialize `_metric_registry` inline like other services — the `super().__init__` pattern meant `_metric_registry` had to be set in `__init__` explicitly, not autogenerated. Always check constructor pattern (direct vs super) for each service.
- **write_metric_if_present already exists**: Don't duplicate — the MetricRegistry enhances/consolidates the existing helper into a class-based service.
- **Ensure MetricType enum has all needed types** before migrating.
- **Batch recording must be atomic** (all or nothing via sequential flushes).
- **Skip None/negative values** in `record_metric()` to preserve existing behavior.
