Sim User Insights Architecture Review

Architectural friction and deepening opportunities for the sim_user_insights module.

Candidates for Deepening

Candidate 1: Extract Insights Computation Module

Files: scripts/build_sim_user_insights.py

Strong

The insight computation logic is intertwined with file I/O and grouping, making it hard to test and reuse.

Problem

The main function handles loading, grouping, and insight building. The insight building function is pure but buried. Unit testing requires mocking file reads.

Solution

Create a dedicated insights module (e.g., sim_user_insights/insights.py) with functions that take in-memory data structures (profiles, history rows) and return insights. This separates computation from I/O.

Benefits

Locality: Changes to insight logic are isolated. Leverage: The insights module can be reused by other scripts (e.g., enrichment) and tested in isolation.

Candidate 2: Modularize OpenFoodFacts Enrichment

Files: scripts/enrich_sim_users.py

Worth exploring

The enrichment script mixes caching, database calls, data transformation, and aggregation.

Problem

The script does too many things: loads data, searches OF (with caching), enriches rows, computes statistics, and writes output. This makes it hard to test individual steps (e.g., the OF search logic).

Solution

Break into modules: of_client.py (handles OF search and caching), enrichment.py (applies OF data to history rows), aggregator.py (computes statistics). The main script orchestrates these modules.

Benefits

Locality: OF search logic can be tested with mocks. Leverage: The OF client could be reused elsewhere in the T1D Companion.

Candidate 3: Pipeline Stages as Separate Modules

Files: scripts/run_structured_companion.py

Speculative

The companion script is a long sequence of stages that are hard to modify or test individually.

Problem

The script has 6 stages (LLM parsing, normalization, DB lookup, LLM review, forecast, advice generation) all in one function. Changing one stage (e.g., switching LLMs) requires touching the entire script.

Solution

Model each stage as a module with a clear input/output interface. Create a pipeline orchestrator that runs the stages. This allows substituting implementations (e.g., different LLM providers) and testing stages in isolation.

Benefits

Locality: Changes to one stage (e.g., prompt tuning) don't affect others. Leverage: Stages can be reused in other contexts (e.g., batch processing of historical scenarios).

Candidate 4: Package-Level Interface for Reuse

Directory: sim_user_insights/

Strong

The module is currently a collection of scripts with no clear library interface.

Problem

Other parts of the T1D Companion (or external tools) cannot easily import and use the sim_user_insights functionality because there is no __init__.py exposing key functions/classes.

Solution

Convert the directory into a proper Python package by adding an __init__.py that exports key functions (e.g., load_profiles, compute_insights, enrich_history, run_companion). This makes it importable as `from sim_user_insights import ...`.

Benefits

Locality: The package boundary is clear. Leverage: Enables reuse in other projects (e.g., the main T1D Companion app) and simplifies testing.

Top Recommendation

Start with Candidate 4: Unified Interface because it enables all other improvements. By making sim_user_insights a proper package, we create a clean boundary that allows extracting modules (Candidates 1-3) without breaking existing scripts. This is a foundational change that improves testability and sets the stage for deeper refactoring.
